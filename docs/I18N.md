# Internationalization (i18n)

Furatena supports multilingual documentation through a **catalog-native** model: translated pages are first-class `DocNode` records linked by `translation_key`, with locale-aware routing, search, and SEO.

This is intentionally **not** a port of Bengal's gettext pipeline. We reuse Bengal's **content conventions** (front matter, subdir URLs) and Chirp core's **UI `t()` catalogs** for chrome strings.

## Two layers

| Layer | Mechanism | What it covers |
|-------|-----------|----------------|
| **Content i18n** | `_locale/{lang}/` overlay + `translation_key` | Markdown pages, nav, search, hreflang |
| **Chrome i18n** | `AppConfig.i18n_enabled` + `locales/*.json` | Sidebar labels, search UI, theme strings |

## Configuration (`docs.yaml`)

```yaml
i18n:
  default_language: en
  fallback_to_default: true
  strategy: subdir            # none | subdir
  locale_content_dir: _locale   # under each mount content_root
  languages:
    - code: en
      name: English
    - code: es
      name: Español
      hreflang: es
```

Enable by listing **more than one language**. With a single language (default), i18n is off and behavior matches the English-only app.

UI catalogs live in `app/locales/` (override with `locales_dir:` in `docs.yaml`).

## Content layout

Default-language pages stay in the existing tree (e.g. `content/chirp/docs/...`).

Translations mirror that tree under an overlay directory:

```
content/chirp/
  docs/get-started/installation.md          # English → /docs/get-started/installation/
  _locale/es/docs/get-started/installation.md   # Spanish → /es/docs/get-started/installation/
```

### Front matter

| Key | Purpose |
|-----|---------|
| `lang` | Explicit locale (optional if path/slug implies it) |
| `translation_key` | Stable ID linking equivalents (defaults to canonical slug) |

```yaml
---
title: Instalación
lang: es
translation_key: docs/get-started/installation
---
```

## URL strategy (`subdir`)

- **Default language** — no prefix: `/docs/...`, `/api/...`
- **Other languages** — `/{lang}/docs/...`, `/{lang}/` for localized home

`edition` (version channel) and `lang` (locale) are **orthogonal**: Spanish docs for v0.3.0 is a supported combination via `doc_version` + locale overlay.

## Catalog graph

Each node carries:

- `lang` — locale code
- `translation_key` — links alternates

Graph edges include `translation` between nodes sharing a key. DCP export records include `lang` and `translation_key`.

## Templates

- `locale_switcher.html` — language links from `doc_languages` context
- `alternate_links` — hreflang `<link rel="alternate">` in `head_meta.html`
- `{% block lang %}` — overridden from `html_lang` / `html_dir` context

## Search

Pass `?lang=es` on `/search` to scope results. Hybrid search filters by node `lang` when i18n is enabled.

## Fallback (`fallback_to_default`)

When a locale URL has no translated page (e.g. `/es/docs/untranslated/`), the app can render the default-language page under that URL with a banner:

- Controlled by `fallback_to_default: true` in `docs.yaml` (default on)
- Template partial: `locale_fallback_banner.html`
- Static export emits fallback locale URLs so GitHub Pages hosts them too
- hreflang alternates only list locales that actually exist (fallback pages are not fake translations)

## Static export

When i18n is enabled, export includes:

- All translated node URLs from the catalog
- Locale home paths (`/es/`)
- Fallback locale URLs for untranslated pages (when `fallback_to_default`)
- Per-locale `index.txt` sidecars including fallback paths

## Sitemap

`sitemap.xml` includes `xhtml:link` hreflang alternates for pages that share a `translation_key`.

## Environment

| Variable | Purpose |
|----------|---------|
| `FURA_LANG` | Override active locale (testing, CI) |

## Resolution service

`LocaleResolutionService` provides locale detection, translated-page lookup,
default-language fallback, language-switcher context, and alternate links
without starting the web app. `DocsApp` delegates request locale behavior to
this immutable service; export and future rendering consumers can use the same
explicit catalog/config boundary.

## Compared to Bengal

| Bengal | Furatena |
|--------|------------|
| Gettext PO/MO | JSON `t()` catalogs (Chirp core) |
| `i18n.strategy` domain/subdir | `subdir` via catalog routes + overlay |
| `alternate_links()` template fn | `alternate_links` in page context |
| Content discovery heuristics | Explicit `_locale/` overlay scan |

## Rollout status

**Shipped in this release:**

- Config + `_locale/` overlay scanning
- `lang` / `translation_key` on nodes + DCP export
- Locale-prefixed routes + language switcher + hreflang
- Locale-scoped nav, search, and graph translation edges
- Chirp `t()` wired for theme chrome when i18n enabled
- **Fallback rendering** for missing translations (`fallback_to_default`)
- **Locale-aware static export** (fallback URLs, index.txt, locale homes)
- **Sitemap hreflang** alternates + multilingual `search.json`

**Future:**

- Domain-based strategy (`es.example.com`)
- Locale-prefixed search routes
